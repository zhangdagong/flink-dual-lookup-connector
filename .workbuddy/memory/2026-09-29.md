## 技术调研：Flink Doris Connector vs JDBC 查 Doris

**关键发现（影响本项目技术选型判断）**：
1. **Doris Connector 的 Lookup Join 底层也是 JDBC** —— 维表必须配 `jdbc-url`，查询走该地址。
   所以它与「JDBC 点查」不是协议之争，差距只在三项工程优化：异步、攒批、缓存。
   （PR apache/doris-flink-connector#97，2023-01 合入，原先基于 Thrift，后改为 JDBC 以支持异步与攒批）
2. `lookup.jdbc.async` **默认 false** → 官方 Connector 默认配置下也是同步逐条点查。
3. 攒批实现是 **UNION ALL 拼接**（`select ... where a=1 union all select ... where a=2`），
   而本项目 `DorisLookupReader` 用的是 `WHERE pk IN (?,?,...)`。
4. **本项目实现已覆盖官方 Connector 的三项优化中的两项**（异步 + 攒批），只缺 lookup 缓存；
   且额外具备官方没有的能力：主备容错、硬超时 + `Statement.cancel()` 真中断后端、HikariCP 连接池、
   `lookup_source`/`lookup_cost_ms` 元字段。**结论：维表点查场景无需换成官方 Connector。**
5. Scan（全量读）才是真正的架构差异：官方走 FE 取 tablet 元数据 → BE 并行直读，数据绕过 FE；
   JDBC 全量读会在单个 FE 上串行，官方明确「不建议使用」。
6. Connector 版本对应：Flink 1.18 用 `flink-doris-connector-1.18`，版本 1.5.2 / 1.6.1。
7. Scan 关键参数：`doris.batch.size`(4064)、`doris.request.tablet.size`(1)、
   `doris.exec.mem.limit`(8192mb，单查询内存上限，共享 BE 时要注意)。
   lookup 关键参数：`lookup.jdbc.read.thread-size`(3，每线程占 1 个 JDBC 连接)、
   `lookup.jdbc.read.batch.size`(128)、`lookup.cache.max-rows`(-1 关闭)、`lookup.cache.ttl`(10s)。

**优化方向（含一次自我修正）**：曾推测「固定 IN 占位符长度 → 命中 FE 计划缓存」。
查证 Doris 官方文档后**予以收回**：Doris 的 PreparedStatement 优化**仅支持单主键等值点查**，
明确不支持 `IN` 列表与嵌套子查询，因此固定 `IN` 长度未必能吃到该路径。此项不再作为优化建议。

## 容量测算：2000 QPS + 5000 万行维表，JDBC 是否有瓶颈

**结论**：2000 QPS 量级下 JDBC 不是瓶颈，但**攒批实际未生效**，且降级时 Doris 要独扛全量。

**关键数据/公式**：
- 并发 = QPS × 单次延迟（不是 QPS 本身）
- 有效批大小 = min(`lookup.batch.size`, 每子任务QPS × `batch.max-wait`)
- 异步算子吞吐上限 ≈ (`buffer-capacity` × 并行度) ÷ 端到端延迟
- 推荐 `buffer-timeout ≈ (batch-size ÷ 预期QPS) × 1.2~2.0`

**重要发现 —— 现配置 `lookup.batch.max-wait=5ms` 会让攒批几乎失效**：
2000 行/秒 ÷ 4 并行度 = 每子任务 500 行/秒，5ms 只能攒到 **2.5 条**
（`batch.size=50` 要 25ms 才攒满，永远达不到）。实际到达 Doris 的 SQL 约 **800 次/秒**，
而非理论上的 40 次/秒。建议把 `max-wait` 调到 **30~50ms**（`lookup.timeout=500ms` 预算内）。

**其余结论**：
1. **5000 万行本身几乎不进公式** —— 点查是 O(log n)，决定速度的是
   ① Unique Key + `enable_unique_key_merge_on_write`；② `store_row_column` + `light_schema_change`
   （决定能否走 SHORT-CIRCUIT 短路径）；③ BUCKETS 分散度；④ 版本数/compaction。
   验证方式：`EXPLAIN` 看计划里有无 `SHORT-CIRCUIT` 标记。
2. 异步算子 `buffer-capacity`（默认 100）是最可能先触顶的一项：延迟从 25ms 抖到 250ms 时
   吞吐上限会跌到 2000/s 以下直接反压，建议显式设 300~500。
3. **降级瞬间 Doris 变唯一源，必须按 2000 QPS 全量规划容量** —— 双源容错最易忽略的一点。
4. 连接数不是问题（`qe_max_connection` 默认 1024，实际占用 = 并行度 × `pool.size` = 32），
   但 `doris.connect.timeout=3000` > `lookup.timeout=500` 是个隐患：池满时业务层先超时，
   而 Doris 是备源、后面没有再次降级 → 整批失败。建议把 connect.timeout 压到 300ms 以内。

**验收方法**：看 `lookup.stats.log-interval` 打出的 `avgBatch`，
若远小于 `batch.size` 即说明攒批被 `max-wait` 卡住。

## 全工程代码审查（未改动代码，仅出结论）

通读 9 个类 + pom + 构建产物 + demo.sql + 仓库状态，共记录 12 项问题。**结论：不是优化项，是两个真 bug。**

**BUG-1（P0，正确性）`DorisLookupReader` 批内重复主键丢数据**
- `:196` `Map<String,Integer> keyIndex` + `:202` `keyIndex.put(joinKey(k), i)` 后写覆盖先写；
  `:328` `keyIndex.get(...)` 只命中最后一个下标，其余下标被 `distribute` 判为「查不到」→ 输出 NULL。
- 交易流水中同一账户在一批内重复出现极常见，属高频路径。
- `HBaseLookupReader` 用 `List<Integer> indexMap` 无此问题 → **两源结果不等价，直接破坏「两源可互换」的核心承诺，
  也违反 README 反复强调的「绝不静默丢数据」**。
- 修法：`Map<String, List<Integer>>`，结果行分发给所有同名下标。

**BUG-2（P1）攒批定时器未取消，残留任务提前冲掉下一批**
- `DualLookupFunction:164` `batchScheduler.schedule(this::flush, ...)` 返回的 `ScheduledFuture` 被丢弃；
  `flush()` 只重置 `flushScheduled=false`，不取消在途任务。
- 时序：t=0 排 5ms 定时器 → t=2 攒满触发 flush 并清空 → t=2.5 新 key 进来再排一个 →
  **t=5 老定时器照常触发，把新批次提前冲掉**。
- 后果：批大小系统性偏小，SQL 次数高于理论值（放大上一轮分析的 FE 压力问题）。
- 修法：保存 `ScheduledFuture` 并在 flush 时取消；或引入 epoch 让过期任务直接返回。

**其余 10 项（P1/P2/P3）**：`stmtRef` 竞态导致超时无法取消排队中的查询（`:255` 把 `task.cancel(true)` 关进
`st != null`）；`queryExecutor` 用无界队列无背压（`:111`）；rowkey 用 `toString()` 而 `decode()` 按类型，
数值型主键按 HBase 惯例写入就查不到（`HBaseLookupReader:297`）；列名 `Bytes.toBytes`/`toLowerCase` 在每行每列
重复计算可提到构造期；`ensureOpened()` 是 synchronized 方法可改双检锁；**fat jar 打包了未 relocate 的
hadoop-common（实测 30,228 个类、72MB），可换 `hbase-shaded-client-byo-hadoop`**；零单元测试；
无 `.gitignore` 且 `.idea/*.xml` 被跟踪；demo.sql 三处笔误。

## 核心语义核实 + 补测试（39 例全绿）
