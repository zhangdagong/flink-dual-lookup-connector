## 第四轮：Doris 宕机场景核查（1 项实测性能缺陷修复，测试 39→40）

**问题**：用户问「Flink 启动时 HBase 正常、Doris 宕机会怎样」。逐路径核查 + 写探针实测（target/dbg 下的 DorisDownProbe / DorisFailoverProbe，验证完已删）。

**结论（分场景）**：
- 默认 lookup.primary=hbase：Doris 全程不被 open()，零连接零日志零代价；代价是这段时间容错能力归零。
- DDL 建表 / 作业提交阶段：参数校验是纯参数检查，不连库，零影响。
- Doris 作主源且宕机：每批降级到 HBase，数据连续。**修复前 1002ms/批，修复后 300ms/批**。

**缺陷（P1，实测而非推测）**：`DorisLookupReader.open()` 指向拒绝连接端口固定耗时 1002ms，裸 JDBC 只需 2~107ms。
反编译 + 读 HikariCP 4.0.3 源码定位：`HikariPool.checkFailFast()` 在首次建连失败后 `quietlySleep(SECONDS.toMillis(1))`，
而 `initializationFailTimeout` 默认 1（>0 表示建池时先抢一条连接）。**修复：`hc.setInitializationFailTimeout(-1L)`**。
效果：open() 1002→0~29ms、opened 保持 true（不再每批重建池）、每批代价被 doris.connect.timeout 封顶、Doris 恢复后池自愈。
加回归测试 `DorisLookupReaderTest` → 断言「Doris 宕机时 open() 不被建池自检拖住」（<500ms 且 opened=true）。

**文档**：README 4.5 惰性建连补 HikariCP 说明、5.2 参数表 connect.timeout 行补「每批代价封顶」、11 排查表加「Doris 宕机作业无反应」行、
13 故障演练补场景 4/5；CODE_REVIEW 新增第七章（场景表 + 7.1 根因/修复/实测对比表）。

**坑**：Git Bash 里 `$(find ...)` 生成的 classpath 是 `/c/...` 形式，Windows 的 javac.exe 不认，必须走 Python 脚本拼 Windows 路径。
