## 第四轮：Doris 宕机场景核查（1 项实测性能缺陷修复，测试 39→40）

**问题**：用户问「Flink 启动时 HBase 正常、Doris 宕机会怎样」。逐路径核查 + 写探针实测（target/dbg 下的 DorisDownProbe / DorisFailoverProbe，验证完已删）。

**结论（分场景）**：
- 默认 lookup.primary=hbase：Doris 全程不被 open()，零连接零日志零代价；代价是这段时间容错能力归零。
- DDL 建表 / 作业提交阶段：参数校验是纯参数检查，不连库，零影响。
- Doris 作主源且宕机：每批降级到 HBase，数据连续。**修复前 1002ms/批，修复后 300ms/批**。

**缺陷（P1，实测而非推测）**：`DorisLookupReader.open()` 指向拒绝连接端口固定耗时 1002ms，裸 JDBC 只需 2~107ms。
反编译 + 读 HikariCP 4.0.3 源码定位：`HikariPool.checkFailFast()` 在首次建连失败后 `quietlySleep(SECONDS.toMillis(1))`，
而 `initializationFailTimeout` 默认 1（>0 表示建池时先抢一条连接）。**修复：`hc.setInitializationFailTimeout(-1L)`**。
效果：open() 1002→0~29ms、opened 保持 true（不再每批重建池）、每批代价被 doris.connect.timeout 封顶、Doris 恢复后池自愈。
加回归测试 `DorisLookupReaderTest` → 断言「Doris 宕机时 open() 不被建池自检拖住」（<500ms 且 opened=true）。

**文档**：README 4.5 惰性建连补 HikariCP 说明、5.2 参数表 connect.timeout 行补「每批代价封顶」、11 排查表加「Doris 宕机作业无反应」行、
13 故障演练补场景 4/5；CODE_REVIEW 新增第七章（场景表 + 7.1 根因/修复/实测对比表）。

## 第五轮：降级日志限流（新配置 lookup.failover.log-interval，测试 40→45）

**问题**：用户反馈主源 HBase 长时间故障 + 每分钟 5000 条流量时，`[dual-lookup] 主源 hbase 批量查询失败，降级到备源 doris。批大小=1`
会刷屏。算下来：83 条/秒、max-wait=30ms → 有效批大小 ≈2.5 → ≈33 批/秒 → 约 285 万行 WARN/天。危害不只是占盘，
而是 TM 日志频繁滚动会把故障起点那几行冲掉。

**设计**：`DualLookupFunction.FailoverLogGate`（静态嵌套类，纯状态机，时刻由调用方传入 → 可直接单测）。
「首条必打 + 按间隔采样 + 合并计数 + 恢复补打」：
- 首条降级 WARN 无条件打印（含完整 cause，故障起点必留痕）；
- 之后每 interval 最多一条，末尾带「距上次打印又发生 N 批降级已被合并」；
- 主源恢复时补一条 INFO「已恢复…本次故障共降级 N 批」并 reset 闸门；
- 新配置 `lookup.failover.log-interval`（秒，默认 10，**0=不限流**即旧行为，负数建表期报错）。

**关键点**：限流只影响打印，不影响 `stats.recordFailover()` 计数——精确总量始终可在统计日志 `failover=` 里求差得到。

**测试（+5）**：`DualLookupFunctionTest` 加 4 例（首条必打+间隔采样+合并计数、interval=0 每批都打、reset 开新周期、
**反射读真实 Function 的闸门验证接线**——纯状态机测试不能证明它真被调用）；`DualLookupOptionsTest` 加 1 例（默认 10、负数拒绝、0 合法）。

**文档**：README §5.1 参数表加行、§8 重写为「两类日志」+ 新增 8.1 日志洪峰小节（含 5000/分 的测算表与三段日志示例）、
§13 校验表加行；demo.sql 加参数与注释；TEST_PLAN 案例 14 加限流说明。顺手修掉 README 章节编号断层（13 → 15 缺 14，统一为 14）。

## ⚠️ 发现：用户运行的是 v1.0 老 jar（所有修复都未生效）

用户贴出统计日志 `[dual-lookup] table=dim_account totalKeys=540 avgBatch=1 | hbase[batches=540 keys=540 fail=0] doris[batches=0 fail=0] failover=0`，
**缺少 `avgBatchWithStandby=` 字段**。逐版本比对确认：

| 版本 | 统计日志格式 | avgBatch 算法 |
|---|---|---|
| `b15edde` (v1.0) | 无 avgBatchWithStandby —— 与用户日志逐字一致 | totalKeys/(主批+备批) |
| `17c9b09` → HEAD | 有 avgBatchWithStandby | primaryKeys/主批 |

进一步用标记法核对 v1.0 缺失项（全部 0 命中）：`normKeyPart`、`pendingFlush`、`setRemoveOnCancelPolicy`、
`HBASE_ROWKEY_ENCODING`、`ASYNC_LOOKUP_TIMEOUT`、`initializationFailTimeout`、`FailoverLogGate`。
即 **19 项修复一个都不在运行的 jar 里**。这也解释了用户此前遇到的「降级 WARN 刷屏」——v1.0 没有限流闸门。

注：`17c9b09` 作者时间是 2026-08-30，仓库里 `b15edde` 是 v1.0 基线。用户每次验证前需 `mvn clean package` 重打 jar
并替换 `$FLINK_HOME/lib` 下的旧包 + 重启集群。

**日志字段速查（当前 HEAD 格式）**：`table` / `totalKeys`（累计 key）/ `avgBatch`（=主源keys/主源批，反映攒批是否生效）/
`avgBatchWithStandby`（含备源）/ `主源[batches keys fail]` / `备源[batches fail]` / `failover`。全部为单调递增累计值，两行相减得区间量。
判定基准：`fail=0 + failover=0 + 备源 batches=0` = 最理想稳态；`avgBatch≈1` 在低流量下是数学必然（有效批大小 ≈ 子任务QPS × max-wait），非配置错误。

   两个口径刻意如此：① 失败批次耗时也计入（否则「主源正在变慢、开始不断超时」这段恶化过程被完全掩盖）；

一旦某行漏打（INFO 被过滤等），清零会把那批数据永久丢掉，相减只会把两个区间合并到下次输出。新增 9 个 `last*` 快照字段，
只在打点线程读写所以无需同步。为不丢长期视角，`close()` 补打一行 `since-start` 累计汇总（有活动才打，避免噪音）。

**可测性改造**：把日志拼装抽成包可见的 `snapshotLine()` / `totalLine()`，测试直接断言文本，不必捕日志（捕日志的测试脆弱且难覆盖边界）。

## 第七轮：每行补上自启动累计视角 + 长期运行开销评估（53 全绿，提交 f8ae135）

用户两点：① 每次打印时把历史累计统计也带上；② 这种统计日志对资源与性能有无影响（Flink 跑好几个月的话）。

**改动**：一行内两个视角，`||` 分隔 —— `window=` 段（本阶段）+ `since-start` 段（自启动累计）。真机实测输出（临时 StatsDemo，跑完即删）：

```
[dual-lookup] table=dim_account window=360s totalKeys=5400 ... failover=2 || table=dim_account since-start totalKeys=9900 ... failover=2
```

- 计数一次性读成**不可变内部类 `Sample`**（9 个 long），两段共用同一快照 → 「本行阶段 + 此前累计 = 本行累计」恒成立。
  若两段各自读原子变量，会出现「累计比阶段少 3 批」这类自相矛盾的数字；原 9 个 `last*` 字段合并为一个 `lastSample`（+`minus`/`sameAs`）。
- `totalLine()` 保留（close 用）；close 补打条件收紧为 `interval>0` + 有活动 + **上次打点后有新活动**（否则与每行 since-start 段重复）。
- **新增 `logSnapshotSafely()` 兜底**：`scheduleAtFixedRate` 在任务抛未捕获异常后会**静默取消后续调度**（不打印不重试，统计永久停摆无人察觉）；
  套 `try/catch(Throwable)` + 首次失败告警一次（`logFailureReported`）。这是本轮唯一的功能性加固。
- `since-start` 语义 = **本统计实例创建以来**，TM 重启（恢复/扩缩容/升级）后归零，不等于作业生命周期总量 —— 已写进所有文档。

**性能结论（第二问，落进 README §8.2 + CODE_REVIEW 12.2）**：打点 CPU 每 6 分钟几十微秒（<0.001%）；
埋点每批 4 次原子自增 <0.1μs vs 每批一次 ms 级 RPC（<0.01%）；常驻内存固定 ~200 字节（无集合/缓存/队列，跑一月=跑一年）；
日志 ~240 行/天/子任务 ≈77KB/天、一年 28MB；不溢出（long 上限 9.22e18，纳秒累计要「1000 批/秒×10ms/批」连跑 29 年，key 数要 5000 万年）。
唯一需运维动作的是日志滚动，而 Flink 1.18 TM appender 默认已是 100MB×10，无需额外配置。一句话：**成本由「每 6 分钟一行」而非「每批一行」决定**。
