## 连续降级告警推 Kafka（v1.3.0，commit 91e7a17）

需求：保持原有功能不变，新增「连续 n 批降级至备源时推自定义 JSON 到可配置 Kafka topic」，n 可配。

### 设计决策（有长期价值）
- **告警语义选「连续」而非「累计」**：主源任意一批成功即清零（重新武装）。累计计数会让稀疏抖动误报。
- **边沿触发而非电平**：只在 `consecutive == threshold` 那一批推一条，之后继续降级不再推。否则持续故障会每 n 批推一条，Kafka 变成第二个日志洪峰。`streak.incrementAndGet()` 返回值全局唯一，`==` 判断天然只被一个线程命中。
- **计数粒度是 per-subtask**：并行度 4 时一次故障最多 4 条，消息里带 `subtask`（如 `1/4`）供下游去重。
- **告警必须是纯旁路**：`KafkaProducer.send()` 在元数据不可用时最多阻塞 `max.block.ms`（默认 60s），在降级回调里直接调用会拖死维表查询。所以调用线程只入队（`ArrayBlockingQueue(8)`），投递在单线程守护线程里做；队列满就丢并 WARN。
- **告警计数与日志限流解耦**：`notifyFailover()` 不复用 `warnFailover()`，否则调 `lookup.failover.log-interval` 会悄悄改变告警时机。
- **可测性拆分**：`FailoverAlertNotifier`（计数/渲染，`Sink` 接口） + `KafkaAlertSink`（真实 Producer）。前者 10 个用例不需要 broker。

### 两个 Kafka 客户端坑
- `acks=1` 与 Kafka 3.x 默认 `enable.idempotence=true` 冲突，生产者构造直接抛 `ConfigException` → 必须显式 `enable.idempotence=false`。
- pom 排除 `zstd-jni` / `lz4-java` / `snappy-java`（省约 8MB）的前提是锁死 `compression.type=none`；要开压缩必须同时改 pom 和 `KafkaAlertSink.producerProps`。

### 其它
- 模板渲染：`${placeholder}` 替换成**已转义、不含引号**的内容，引号由模板作者加。建表期校验三项：非空 / 占位符闭合且在白名单 / 首尾 `{}` 或 `[]`。
- 校验顺序刻意设计成「非空 → 占位符 → JSON 外形」，让 `{"n":${x` 报「未闭合」而不是笼统的「不是 JSON」。
- `KafkaProducer.close(Duration)` 自带冲刷，不要再 `flush()`（它无超时上限，最坏等 `delivery.timeout.ms`=15s，会让「关闭有超时」失效）。
- 版本 1.2.9 → 1.3.0，fat jar 29MB → 34MB，用例 95 → 116。

### 本机构建方式（无 mvn）
IDEA JBR 的 `javac.exe` + `~/.m2` 全量 classpath + `JUnitCore`；脚手架在 `%TEMP%\dual-build\build.py`（不入库）。
坑：`@argfile` 内反斜杠是转义符，路径必须转正斜杠；classpath 需按版本过滤 slf4j-api（保留 1.7.36）、排除 guava-16、`hbase-shaded-client` 只留 `byo-hadoop-2.2.7`（后者带 JDK18+ DNS SPI 声明，会让 kafka-clients 测试报 `DnsjavaInetAddressResolverProvider not found`）。
