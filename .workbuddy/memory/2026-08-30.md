## 新建 Flink 双源容错 Lookup Connector（HBase / Doris）

工作区 `C:\Users\Admin\WorkBuddy\FlinkSQLConnector`，从零搭建 Maven 工程，
connector id = `dual-lookup`，包路径 `com.roc.flink.connector.dual`。

### 需求
Kafka 流进入后查维表，HBase 与 Doris 中有同名同构表，优先查其一（可配主备），
出现 500ms 超时 / 服务异常 / 表异常时自动切另一个源。

### 方案选型（已确认，不要再退回 UNION 方案）
- **否决**「两条 Lookup Join + UNION ALL」：每条数据都查两个源、吞吐减半、
  无法精确控制单次超时、故障期慢源持续拖尾。
- **采用**自定义 `LookupTableSource`：对 SQL 完全透明，一条 Lookup Join 搞定。
  内部 `FailoverRouter` 做主备路由 + 三态熔断。

### 实现要点
1. **熔断后直接走备源，不再空等超时** —— 否则主源整体宕机时每条数据白等 500ms，吞吐塌方。
   状态机 CLOSED → (连续失败 N) → OPEN → (冷却) → HALF_OPEN → (连续成功 M) → CLOSED。
2. **Doris 超时必须调 `Statement.cancel()`**，不是 thread.interrupt（JDBC 不响应 interrupt），
   否则慢查询堆积会把连接池耗光。
3. **查不到数据 ≠ 故障**：空结果是正常业务结果，不计入失败、不触发降级；
   需要主源查不到时回查备源才开 `lookup.fallback-on-empty`。
4. **负缓存**：空结果也进缓存，避免不存在的 key 反复穿透。
5. **惰性建连**：Reader 不在算子 open() 时建连接，而是首次查询时建。
   主源在作业启动时刻不可用时，作业仍能正常启动并直接走备源，后续由半开状态自动重连。
6. **三层超时**：客户端层（hbase.rpc.timeout / doris.query.timeout）
   < 业务层（lookup.timeout）< 算子层（table.exec.async-lookup.timeout，经验值 = lookup.timeout×2+2s）。
7. 可选对冲请求 `lookup.hedge.*` 压低 P99（默认关）。

### Flink 1.18 API 陷阱（重要，已踩过）
- `AsyncLookupFunction` 与 `LookupFunction` 都在 **`org.apache.flink.table.functions`** 包，
  **不是** `org.apache.flink.table.connector.source.lookup`（只有 *Provider 类在后者）。
- 1.18 起二者是**抽象类**，要实现的是：
  - 同步 `Collection<RowData> lookup(RowData keyRow)`
  - 异步 `CompletableFuture<Collection<RowData>> asyncLookup(RowData keyRow)`
- 基类的 `eval(...)` 是 **final**，不能覆盖（覆盖会编译报错）。
- 键值从 `keyRow` 按位置取，顺序与 DDL 主键声明一致，值是 Flink 内部表示
  （StringData / DecimalData / TimestampData / int 等），需按 LogicalType 用对应 getter。
- Provider 仍是 `LookupFunctionProvider.of(LookupFunction)` /
  `AsyncLookupFunctionProvider.of(AsyncLookupFunction)`。
- 异步是否生效由 hint 控制：`LOOKUP('table'='x','async'='true')`；
  connector 提供异步能力后 planner 默认倾向异步，`async='false'` 才走同步。

### 其他坑
- `final transient` 字段反序列化后是 **null**（final 不会被重新初始化）→ 会 NPE。
  熔断器 map 等非序列化字段不要加 final，改为在 open() 中赋值。
- 共享逻辑用 **static 嵌套类**（如 `LookupCore`），不能用匿名内部类捕获外层 Function this，
  否则序列化循环引用。

- 目标版本：Flink 1.18.1 / HBase 2.6.1 / Doris 4.0.8（MySQL 协议）/ HikariCP 5.1.0。

## 第十轮：LOOKUP hint 的 'table' 必须用 FROM 别名（若有别名）

第九轮改成逻辑表名 `dim_account` 后仍报 `cannot match ... dim_account in LOOKUP`。

**最终正确规则**（已用官方 javadoc 核实）：
> `'table'` 的值必须与 FROM 子句中该表的**引用名**一致；**若表起了别名，必须填别名**，不能用表名。

官方原话：*"only table name is supported (keep consistent with which in the FROM clause), note that only alias name can be used if table has an alias name."*

例：`LEFT JOIN dim_account FOR SYSTEM_TIME AS OF t.proc_time AS m1` → hint 写 `'table'='m1'`。

- 修复：demo.sql 的 hint 从 `dim_account` 改成 `m1`；README 快速开始示例的 hint 也改成别名 `d`。
- 教训：LOOKUP hint 的 table 匹配的是"FROM 引用名"（有别名用别名、无别名用表名），不是 DDL 表名、更不是物理表名。

## 第十二轮：修复 HBase「waiting for region location」冷启动超时

WARN 日志生效后暴露真问题：降级根因是
`RetriesExhaustedException ... TimeoutIOException: Timeout(499ms) waiting for region location for dim:dim_account, row='100007'`

**根因**：HBase 客户端**冷启动**——首条查询某表前，要先从 hbase:meta 定位 region 在哪台 RegionServer，
这一步要数百毫秒，正好撞上 500ms 超时被判降级。缓存建立后查询只需几毫秒。

**两层解决**：
1. `HBaseLookupReader.open()` 建连后**预热 region location**，把冷启动开销挪出查询路径：
   ```java
   table.getRegionLocator()
       .thenCompose(locator -> locator.getAllRegionLocations())
       .get(cfg.hbaseOperationTimeoutMs, TimeUnit.MILLISECONDS);
   ```
2. 调大客户端超时（给 region location 定位留足时间，业务降级仍由 lookup.timeout 独立控制）：
   - `hbase.rpc.timeout` 300 → 600
   - `hbase.client.operation.timeout` 500 → 2000

### 关键认知
- `lookup.timeout` 是业务层**独立硬超时**（ScheduledExecutorService 强制），与 HBase 客户端内部超时（rpc/operation timeout）是两套并行机制，不是严格层级关系。
- 之前的"rpc.timeout < lookup.timeout"说法不准确，已在 README 纠正为三套独立超时。
- 用户已自行把 demo.sql 的 lookup.timeout 调到 1000ms、zk 127.0.0.1、doris.table-name 用 `dim.dim_account`（库名）。

### 修正：getRegionLocator() 返回类型
预热代码最初写成 `table.getRegionLocator().thenCompose(locator -> locator.getAllRegionLocations())`，IDEA 报"无法解析 getAllRegionLocations"。
**根因**：`AsyncTable.getRegionLocator()` 是**同步返回 `AsyncTableRegionLocator`**（不是 `CompletableFuture<...>`），
而 `getAllRegionLocations()` 才返回 `CompletableFuture<List<HRegionLocation>>`。正确写法：
```java
table.getRegionLocator().getAllRegionLocations().get(timeoutMs, TimeUnit.MILLISECONDS);
```
教训：HBase AsyncTable 的 getRegionLocator 与 getTable/getRegionLocations 的异步风格不同，别想当然。

   - `LookupReader` 接口由单条 `lookupAsync(Object[])` 改为批量 `batchLookupAsync(List<Object[]>)`，返回 `Map<下标, List<Map>>`（未命中下标不出现在结果里）。
   - `DorisLookupReader`：单主键 `WHERE pk IN (?,?,...)`，复合主键 `(a=? AND b=?) OR ...`；
     用「主键值拼接（\u0001 分隔）→ 下标」映射反查结果归属 key。
   - `HBaseLookupReader`：`table.get(List<Get>)` 返回 `Result[]`，下标与 Get 一一对应，按 indexMap 映射回原 key。
   - `DualLookupFunction`：攒批缓冲（batchKeys+batchFutures+lock），攒满 `batch.size` 或定时 `batch.max-wait` 触发 flush；
     flush 在**锁外**执行批量 IO（避免持锁阻塞入队）；批量查主源、失败批量降级备源、按 key 分发。
   - 关键细节：`lock` 不能 final transient（反序列化后为 null），在 ensureOpened 里 new。
3. **统计日志**：新增 `LookupStats`，统计主/备源批次数、key 数、失败数、降级次数、平均批量，定时打一行。
4. **Doris 连接池参数**：新增 min-idle / idle-timeout / max-lifetime / validation-timeout（HikariCP 对应项）。

### 降级语义（确认）
`doBatchLookup` 里 `whenComplete((resultMap, ex) -> ex==null ? 分发 : 降级)`：
- 超时（reader 内部 completeExceptionally(TimeoutException)）→ ex!=null → 降级
- 其他异常（连接失败/表异常）→ ex!=null → 降级
- 查到空数据 → ex==null、resultMap 缺该 key → 不降级

### 规模
9 个 Java 文件，1614 行（攒批与批量查询是必要复杂度）。新增 LookupStats.java。

### 编译踩坑（HBase 批量 get 的返回类型）
- `AsyncTable.get(List<Get>)` 返回的是 **`List<CompletableFuture<Result>>`**，不是 `CompletableFuture<Result[]>`！
  上一版误写成 `table.get(gets).whenComplete(...)`，报"无法解析 List 中的方法 whenComplete"。
- 正确写法：`List<CompletableFuture<Result>> futures = table.get(gets)`，再用
  `CompletableFuture.allOf(futures.toArray(...)).whenComplete(...)` 组合等待，逐个 `futures.get(j).join()` 取结果。
- 教训：HBase AsyncTable 的 `get(Get)` 返回 `CompletableFuture<Result>`（单条），`get(List<Get>)` 返回 `List<CompletableFuture<Result>>`（批量），二者包装层级不同，批量不能当单条链式调用。

## 第十四轮：Kerberos 支持 + 健壮性检查 + README 优化

### 1. HBase Kerberos 支持
- **关键认知**：HBase 2.2.0+ 的 `ConnectionFactory` 内置 keytab 自动登录 + TGT 续期，
  只需设置 `hbase.client.keytab.file` + `hbase.client.kerberos.principal` 两个配置，
  **无需**手动 `UserGroupInformation.loginUserFromKeytab`（这是官方推荐做法，最精简）。
- 新增配置项：`hbase.security.authentication`（默认 simple）、`hbase.client.keytab.file`、
  `hbase.client.kerberos.principal`、`hbase.regionserver.kerberos.principal`、
  `hbase.master.kerberos.principal`、`hbase.kerberos.krb5.conf`。
- HBaseLookupReader.open() 里建连前调 `applyKerberos(conf)`；krb5.conf 通过 `java.security.krb5.conf` 系统属性指定。
- 校验：kerberos 下 keytab + principal 必填。

### 2. 检查发现并修复的问题
- **Doris 连接/线程打满风险（真实问题）**：`doris.query.timeout`（秒）若 > `lookup.timeout`，
  慢查询在业务层超时降级后仍占着 queryExecutor 线程 + HikariCP 连接，直到 JDBC 层才中止，会打满池子。
  修复：JDBC queryTimeout 自动 clamp 到 `min(doris.query.timeout, ceil(lookup.timeout/1000))`。
- **close() 积压 future 不完成（轻微）**：作业取消时攒批缓冲里的 future 永不 complete，异步算子可能卡住。
  修复：close() 里把积压 future 补空。
- 其余审查结论（无泄漏）：HBase AsyncConnection/Doris HikariCP/各线程池 close 均已释放；
  HBase 空 key 过滤、元字段 NULL 语义均正确。
